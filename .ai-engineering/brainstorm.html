01The Idea in Plain Words

You want a personal iPhone and Apple Watch app that connects via Bluetooth to 2–5 RGBCCT LED controllers (each in a different room or zone). The app gives you a full visual interface on iPhone: a color picker that handles both hue/saturation and warm-to-cool white temperature, an intensity slider, and a simple weekly scheduler (different on/off times for weekdays vs weekends, with a target color and brightness). Every action — power, color, intensity, color temperature, schedule enable/disable — is also exposed to Siri through App Intents so you can say things like "Hey Siri, turn on the bedroom lights" or "Set the living room to warm white at 50 percent" from your iPhone or Apple Watch. You will provide the current iOS app you use today so the Bluetooth protocol can be reverse-engineered. The app is for personal use only, distributed via Xcode or TestFlight, with no iCloud sync, no HomeKit, no family sharing.

02Why This Matters

The existing LED controller app lacks Siri integration, forcing manual app interaction for every change. Voice control is the natural interface for ambient lighting — you shouldn't need to unlock your phone, find the app, and tap buttons just to dim the lights or change the mood. A personal app also avoids the limitations of commercial solutions (subscription fees, cloud dependence, limited customization) and gives you full ownership of the scheduling logic and Siri phrases.

03Who It's For

Single user (you), personal use across one iPhone. No sharing, no multi-user accounts, no family sync. The app is built for your specific hardware and your specific rooms.

04What Exists Today

  • An iOS app (provided by you) that controls the LED controllers via Bluetooth
  • 2–5 physical LED controllers, each exposing a Bluetooth LE service with one or more writable characteristics
  • RGBCCT (5-channel) LED strips: Red, Green, Blue, Warm White, Cool White
  • No public documentation for the Bluetooth protocol — will be discovered during development via trial-and-error with nRF Connect
  • No existing codebase for this new app — greenfield project

05What Success Looks Like

  • App launches, scans, and pairs with all 2–5 controllers reliably
  • Visual control screen lets you pick any RGBCCT color and intensity smoothly
  • Weekly schedules fire on time (weekdays vs weekends) even when app is not running
  • Siri responds to natural commands for every controllable parameter
  • Apple Watch app provides quick control (power, intensity, color temp) and Siri works from wrist
  • No crashes, no Bluetooth connection leaks, battery-friendly background operation
  • Installs via Xcode / TestFlight on your iPhone (iOS 17+) and Apple Watch (watchOS 10+)

06Decisions Already Made

Locked Decisions

  • Platform: iOS 17+ and watchOS 10+ (SwiftUI, SwiftData, App Intents, BackgroundTasks)
  • Architecture: SwiftUI + SwiftData + CoreBluetooth (MVVM, no TCA, no Realm)
  • Siri: App Intents (iOS 16+), not legacy SiriKit/Shortcuts
  • Distribution: Personal — Xcode install / TestFlight only
  • Sharing/Sync: None — local only, no iCloud, no HomeKit
  • Color format: RGBCCT (5 channels: RGB + warm white + cool white)
  • Scheduling: Simple weekly — weekday on/off times, weekend on/off times, target state per schedule
  • Devices: 2–5 controllers, each named by room/zone
  • UI: Full tabbed interface (Devices, Control, Schedules, Settings) + Lock/Home screen widgets + Apple Watch app
  • Background execution: BGAppRefreshTask every ~15 min + local notification fallback + bluetooth-central background mode
  • Reverse engineering: Protocol will be discovered iteratively during development using nRF Connect on Windows; initial LEDCommandEncoder will use placeholder/guessed format, refined as commands are tested

07Decisions Still Open

Open Decisions (User Must Close)

  1. Scene presets: Decided: No — not including named scenes
  2. Query intents: Decided: Yes — add "Hey Siri, what's the bedroom light status?" read-only intents
  3. Widget timeline: Decided: Yes — widgets show current state and next scheduled change
  4. Animation/transition support: Decided: Only if hardware supports it — discover during reverse engineering
  5. Error/notification UX: Decided: Yes — local notifications when schedule fails to execute

08Constraints and Guardrails

  • iOS 17+ / watchOS 10+ only — no backward compatibility code
  • Personal distribution — no App Store review constraints, but also no push notification service (APNs) unless you configure it
  • Bluetooth LE only — no Thread, Matter, Wi-Fi, or Zigbee
  • Single iPhone + Apple Watch — no multi-device sync, no tvOS/macOS/visionOS targets
  • SwiftData local-only — CloudKit container disabled
  • Background execution budget — BGAppRefreshTask ~15 min intervals; cannot guarantee exact-minute firing
  • Reverse engineering required — protocol unknown until capture completed
  • Watch limitations: watchOS cannot run long background tasks; Bluetooth operations must be fast; UI is glanceable not full-featured

09Out of Scope

Explicitly Not Building

  • HomeKit / Matter integration
  • iCloud sync or multi-device support
  • Family sharing or multi-user accounts
  • App Store release (no review prep, no privacy manifest for tracking)
  • tvOS, macOS, visionOS targets
  • Firmware updates for the LED controllers (DFU)
  • Complex scene editor (timelines, animations, music sync)
  • Remote control over internet (no cloud bridge)
  • Third-party voice assistants (Alexa, Google Assistant)
  • Named scene presets (Movie Night, Reading, etc.)

10Open Questions for Research

  1. Bluetooth protocol: What are the service UUID, characteristic UUIDs, and exact byte format for each command? Will be discovered iteratively during development using nRF Connect on Windows; initial implementation uses best-guess format for common RGB controllers.
  2. Controller capabilities: Does hardware support fade transitions, stored scenes, or read-back of current state? Affects UI polish and Siri query intents; discover during manual testing.
  3. Connection stability: How do controllers behave after hours/days of inactivity? Do they advertise continuously? Affects reconnection logic and background scheduling reliability.

11Handoff Notes

  • Start with: Xcode project setup (SwiftUI, SwiftData, CoreBluetooth, App Intents capabilities), add Watch target, then BLEManager actor skeleton
  • Parallel track: Protocol discovery — use nRF Connect Windows to test commands against hardware; update LEDCommandEncoder as format is discovered
  • Data models first: LEDDevice, WeeklySchedule in SwiftData (no LEDScene)
  • App Intents early: Define entities and intents alongside data models so Siri integration isn't an afterthought; include query intents for status
  • Widgets: Add Widget Extension target; timeline provider reads SwiftData
  • Apple Watch: Add Watch App target (watchOS 10+); share BLEManager and models via shared framework or package; UI: simple list of devices with power toggle, intensity slider, color temp picker; App Intents automatically available on Watch via same intent definitions
  • Background tasks: Register BGAppRefreshTask in AppDelegate / @main; schedule evaluation logic shared with widget timeline
  • Testing: Unit test LEDCommandEncoder against discovered protocol; UI test scheduler logic with mocked time; test Watch app in simulator
  • Relevant files to create: BLEManager.swift, LEDCommandEncoder.swift, Models.swift, Intents.swift, WidgetProvider.swift, ScheduleEngine.swift, WatchApp/ target
